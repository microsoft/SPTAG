# 讨论稿：单簇是否意味着重复向量？

[RaBitQ 实现说明](RaBitQ.md) | [当前实验](../../evaluation/2026-11-18-sift10m-rabitq-ip/README.md)

**核心问题：`numClusters <= 1` 只说明这次聚类没有分出多个非空簇，不能单独证明输入是重复向量。**
未归一化 IP 下，大模长中心吸引不同向量是一个直接反例。
精确 L2 没有同样的必然吸附现象，但当前采样聚类流程也不构成重复性证明。

本文用于讨论算法假设和处理策略，不是新的实验报告，也不宣称已经完成 L2 的失败复现。

## 1. 原代码依赖了什么假设？

需要区分三个命题：

1. 这次聚类只得到一个非空簇。
2. 这些条目具有相同的向量表示，可以共享查询分数。
3. 这些条目可以合并，甚至从 posting 中移除，而不影响索引语义。

原来的部分处理近似依赖 `1 => 2 => 3`，但这两步都需要额外条件。
聚类结果不是相等性检查；向量相同也不等于业务 ID、元数据或版本相同。

| 位置 | 原有处理 | 隐含前提 |
| --- | --- | --- |
| [BKTree.h](../../AnnService/inc/Core/Common/BKTree.h)，`KmeansClustering` | 统计 `args.counts[k] > 0` 的数量，返回 `numClusters` | 返回的是非空簇数，不是重复性判断 |
| 同文件，`BuildTrees` / `BuildTreesParallel` 的单簇分支 | 设置负 `childStart`，建立 `m_pSampleCenterMap`，进入重复组表示 | 组内成员可以共享代表点的查询分数 |
| [BKTIndex.cpp](../../AnnService/src/Core/BKT/BKTIndex.cpp)，搜索中的重复组路径 | 使用代表点的 `gnode.distance` 处理组内候选 | 成员对当前查询的分数确实相同 |
| [ExtraDynamicSearcher.h](../../AnnService/inc/Core/SPANN/ExtraDynamicSearcher.h)，`Split` 的单簇分支 | 根据 `m_oneClusterCutMax`，只保留一个或 `m_postingSizeLimit` 个条目 | 被截掉的 posting 条目不再需要保留 |

最后一项是截断**这个 posting 的条目**，不等于代码同时删除了全局样本、元数据或其他 posting 副本。
反过来，也不能仅凭全局样本数量正确，就证明这些条目仍能通过搜索路径被找到。

## 2. IP 的直接反例：不同向量选择同一个中心

使用未归一化内积，距离分数为：

```text
d(x,c) = C - dot(x,c)
```

`C` 是固定常数，不影响中心选择。取 `C=1`，两个不同向量及中心为：

```text
x1 = c1 = (1,0)
x2 = c2 = (2,0)
```

| 输入 | 到 c1 的 IP 分数 | 到 c2 的 IP 分数 | 选择 |
| --- | --- | --- | --- |
| x1 | 0 | -1 | c2 |
| x2 | -1 | -3 | c2 |

虽然两个中心本身就是不同的数据点，所有点仍选择 `c2`，只剩一个非空簇。
查询 `q=(1,0)` 对 `x1`、`x2` 的分数分别是 `0`、`-1`，不能共享代表点分数。

这不是仅限于两个点的边界情形。对任意正数序列：

```text
x_i = (a_i, 0),  0 < a_1 < ... < a_N
```

只要候选中心也是这些同向向量，所有点都会偏好其中模长最大的中心。
可以令 `N` 大于 BKTree 的叶子大小，或令 posting 条目数超过拆分阈值。
上面的两点例子只说明分配规则，不声称两条数据就会触发实际拆分分支。

一般情况下，获胜者是**内积最大的中心**，不一定是全体中心中模长最大的那个。
同方向时，模长优势才直接决定这里的结果。

当前 `TryClustering` 最后的全量分配使用 `lambda=0`，所以不能仅靠训练迭代中的
平衡惩罚推断最终仍有多个非空簇。RaBitQ 的估计误差可能影响具体分配，
但上述反例在精确 IP 下就已成立，不需要量化误差才能解释。

## 3. 为什么精确 L2 的直觉不同，但仍不足以证明重复？

对精确平方 L2：

```text
d(x,x) = 0
d(x,y) > 0, 如果 x != y
```

如果最终中心是两个不同的数据点，且分配时没有额外惩罚，那么它们至少各自会选择自己，
不会出现上面“两个不同中心都被其中一个吸走”的情况。

但这只能推出：**不同的数据点中心能够保住各自的簇**。
不能推出：**实际算法只返回一簇，就说明整个输入只有一种向量**。
尤其不能默认初始化、采样、空簇处理和停止条件一定会找到两个不同中心。

### 一个针对当前采样流程的条件性构造

考虑大量 `a=(0,0)`，以及少量不同的 `b=(10,0)`，要求分成两簇。
假设本次随机初始化的两个中心都是 `a`，参与训练的样本也全是 `a`：

1. 训练中的距离和中心变化都可以为零；空簇修复也可能找不到不同的样本。
2. `currDiff < 1e-3` 满足停止条件，中心仍然重合。
3. 后面的全量分配虽然看到了 `b`，但它到两个相同中心的距离都是 `100`，
   按相同的 tie-breaking 规则进入同一个簇。
4. 当前全量分配后的代表点选择取最近成员，因此代表仍可能是 `a`；
   再次分配仍只得到一簇，但输入确实包含 `b`。

这描述了代码允许的状态路径，**不是声称已经用当前程序和某个固定随机种子跑出了该失败**。
触发概率、当前采样规模下的频率，以及后续查询是否实际丢失 `b`，需要定向回归验证。
不能把这个构造标成已测出的 SIFT L2 故障。

另外，RaBitQ 的近似 L2 估计不能未经验证就继承精确 L2 的全部性质，
更不能用一个近零估计值代替向量表示相等的检查。

## 4. 当前 IP 补丁解决了什么，没解决什么？

| 场景 | 当前处理 | 目的及代价 |
| --- | --- | --- |
| BKTree 单簇 | 保留各个向量作为独立叶子候选，不进入重复组优化 | 不错误共享分数；可能形成较大的叶子组，增加搜索开销 |
| 动态 posting 单簇且至少有两个有效条目 | 按 posting 行号排序并按数量平分，各组选实际条目作代表；包含旧 head 的组优先复用它 | 避免这个单簇分支直接截掉有效条目；不是按距离得到的优质分区，可能增加后续维护成本或影响 recall |

两处都仅针对 IP，没有修改 L2/Cosine 的这两个分支，也没有给输入加归一化。
这是当前改动范围，**不是对 L2 原逻辑正确性的证明**。
posting 的平分兜底只保留进入该分支的有效条目；它不是对所有后续合并、重分配、
物理存储及查询可达性的完整保证。

直接将所有向量归一化会把未归一化 MIPS 改成 cosine，改变检索目标，不能作为等价修复。
仅在建树分区时归一化中心、采用其他分区距离等方案，可以讨论，但属于新的索引策略，
需要保留原始 IP 查询语义并单独评估路由、recall 和维护成本。

### 不要混淆另一个独立问题

`Split` 原来的 `distance(oldHead,newCenter) < Epsilon` 被用来识别同一个 head。
IP 分数可以为负，不同向量也会满足这个条件。当前 IP 路径改为比较代表条目的 VID。
这是**身份判断错误**，与本文的**单簇是否等于重复**是两个问题，不能用一次整体跑通
证明两个修改各自的必要性或效果。

## 5. 建议与同事讨论的决策

1. **重复的定义是什么？** 相同坐标、相同完整量化表示，还是相同 VID 和版本？
   比较量化表示时必须包含影响分数的因子、质心 ID 等，不能只比较 packed bits。
2. **什么情况下允许共享分数？** 是否要求在同一模型和查询模式下，
   对任意查询都具有相同的打分行为，而不是只在当前中心上距离相近？
3. **什么情况下允许丢弃 posting 条目？** 即使坐标相同，不同 ID 也可能需要分别返回；
   副本覆盖、删除/版本语义、过滤与元数据约束是否提供了额外保证？
4. **聚类失败如何处理？** 在验证重复后使用已有优化，还是重选不同中心、增加采样、
   保留大叶子或按数量拆分？如何控制重试、递归拆分、I/O 和查询开销？
5. **是否统一到所有距离类型？** 让“聚类退化”和“确认重复”成为不同状态，
   而不是长期用 `numClusters <= 1` 同时表达它们？

建议验证至少区分：同向不同模长的 IP 输入、采样可能遗漏少数异类的 L2 输入、
坐标完全相同但 ID 不同的输入，以及实际 RaBitQ 编码。
分别检查分区后的 ID 保留、查询候选及分数、保存重载、后续插入和查询成本。
大规模样本数量检查与平均 recall 不能替代这些针对具体假设的验证。

**本稿的结论是需要拆开这几个假设，不是已经证明哪一种兜底策略最优。**
