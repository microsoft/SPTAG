# TiKV distributed posting storage

[Documentation index](README.md) | [Architecture](Architecture.md) |
[Benchmark methodology](Benchmarking.md)

Use this backend when SPANN dynamic postings should reside in a TiKV storage
cluster rather than a local posting store. Applications continue to use the
SPTAG index interfaces; this is a storage integration, not a separate search SDK.
It is implemented but remains an experimental deployment profile until a
specific cluster/version/workload combination is validated.

**To reproduce the FILEIO/TiKV benchmark**, go directly to the
[SIFT1M setup and run guide](../evaluation/2026-10-28-sift1m/Reproduce.md).
It includes dependencies, the build, a pinned single-host cluster and workload
commands; you do not need to execute this page's build steps first.
The sections below explain the integration for other deployments.

## What changes with TiKV

| Component | Location / responsibility |
| --- | --- |
| Dynamic postings and configured backend/version state | TiKV RawKV, with SPTAG-specific operations where required |
| Head index, ID mappings, and local index metadata | Still local to the index instance; coordinate their lifecycle and backups |
| PD/TiKV availability, replicas, topology, and upgrades | Operated as a separate storage cluster |
| Distributed partitioning and index construction | A different workflow; see [construction architecture](Architecture.md#construction-and-multi-layer-indexes) |

TiKV storage does not by itself distribute all search computation, move the
complete index into the cluster, or establish a highly available vector-serving
system. Learn the [small STATIC SPANN path](QuickStart.md#spann-disk-backed-search)
first, then validate the dynamic backend and update semantics separately.

## Requirements and scope

- Linux baseline dependencies and a C++20 compiler.
- gRPC/Protobuf development libraries and code generators from a consistent
  installation.
- A separately deployed, compatible PD/TiKV cluster with reachable advertised
  addresses. Record exact source commits or immutable image digests.
- Separate local index/run directories and TiKV key prefixes for independent
  experiments.

This repository does not currently provide a certified TiKV/PD release pair.
Historical personal forks or `nightly` tags are not stable compatibility pins.
Native Windows and multi-host fault recovery are outside baseline validation.

## Build

From the repository root on Ubuntu:

```bash
sudo apt-get install -y protobuf-compiler libprotobuf-dev libgrpc++-dev \
  protobuf-compiler-grpc pkg-config libabsl-dev

bash ThirdParty/kvproto/generate_cpp.sh
cmake -S . -B build-tikv -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DFOLLY=OFF -DTBB=ON -DSPDK=OFF -DROCKSDB=OFF -DTIKV=ON -DGPU=OFF -DRABITQ=OFF
cmake --build build-tikv --target SPTAGTest spfresh --parallel 2
```

Regenerate the vendored kvproto sources using the same Protobuf installation
used by CMake; headers generated by another Protobuf version can be incompatible.
The generation script refreshes all gRPC stubs, including empty service files.
The TiKV test executable also links Abseil synchronization directly.
Review generated changes rather than committing unrelated regeneration.
Linux artifacts are under the source-root `Release` directory.

## Connect a cluster

Confirm both PD health and that TiKV stores are Up, for example:

```bash
curl --fail http://127.0.0.1:2379/pd/api/v1/health
curl --fail http://127.0.0.1:2379/pd/api/v1/stores
```

Use the actual PD address, not necessarily localhost. Every TiKV store address
returned by PD must be reachable from the SPTAG client. Choose API-version
settings compatible with the client's RawKV requests and test the exact
deployment; a reachable PD endpoint is not sufficient validation.

Deployment topology, resource limits, Raft replication, and data lifecycle are
the cluster operator's responsibility. For the benchmark's isolated local
cluster, use the [current setup recipe](../evaluation/2026-10-28-sift1m/Reproduce.md#6-create-an-isolated-local-tikv-cluster).
Other [evaluation records](../evaluation/README.md) include historical,
machine-specific deployments.

## Configure and run

Use the full harness configuration in [the benchmark guide](Benchmarking.md).
The [SIFT1M report](../evaluation/2026-10-28-sift1m/README.md) describes the
available measurements and their limits. Follow its
[step-by-step instructions](../evaluation/2026-10-28-sift1m/Reproduce.md)
to build and evaluate a new FILEIO/TiKV index.
Storage settings belong in `[BuildSSDIndex]`:

```ini
[BuildSSDIndex]
Storage=TIKVIO
TiKVPDAddresses=127.0.0.1:2379
TiKVKeyPrefix=unique_run_identifier
```

The harness thread keys are `NumSearchThreads` and `NumInsertThreads` in
`[Benchmark]`, not `NumThreads`. Supply real existing vector/query files.
Use `TruthPath=none` only for a functional experiment without recall claims.

From your run directory, after setting `SPTAG_ROOT` to the source checkout:

```bash
BENCHMARK_CONFIG="$PWD/benchmark.ini" \
BENCHMARK_OUTPUT="$PWD/output.json" \
  "$SPTAG_ROOT/Release/SPTAGTest" \
  --run_test=SPFreshTest/BenchmarkFromConfig --log_level=message
```

Verify the actual backend in startup logs, the input counts, completed phases,
and output JSON. An unset `BENCHMARK_CONFIG` skips the test.

## Operational constraints

- **Isolation:** fresh key prefixes prevent experiments from sharing a namespace;
  they do not automatically delete old data.
- **Initial counts:** dynamic index construction initializes TiKV version-map
  counts and upper-layer membership before writing postings. Validate save/load
  and the reported vector count before treating a build as complete. Insertions
  also extend the version-map count, including implicitly alive leaf-layer IDs.
- **Persistence:** TiKV durability covers the data stored there, not missing
  local head/index files. Coordinate backups and compatible restore points.
- **Concurrency:** the implementation includes ordinary merge and CAS-specific
  paths. Do not generalize one path's atomicity to every posting mode; in
  particular, CAS support is restricted for multi-chunk posting operations.
- **Client lifecycle:** thread-local stub-cache entries are weak references;
  each client owns its connection pools. Reloading an index must not retain
  an old client's pools or reuse them when a new client occupies the same
  address. The `TiKVIOTest` regression covers repeated asynchronous reads and
  pool release across client destruction/reconstruction without a TiKV cluster.
- **Routing:** PD/Region/store discovery, retry, and cache invalidation exist,
  but retry limits and failure behavior depend on the operation. Test faults
  against your chosen revision rather than assuming a universal retry count.
- **Validation:** include build, read/write/update, restart/save/load,
  concurrent access, and relevant failure/retry tests before promoting a setup.

For developer context, see the
[distributed version-map design](TiKVDistributedVersionMapDesign.md). It is a
design record, not a guarantee that every proposal is implemented.
